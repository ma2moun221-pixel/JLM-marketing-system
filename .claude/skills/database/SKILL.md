# Database

Best practices for schema design and data access in a Next.js project.

## Schema design

- Normalize by default; denormalize deliberately (and document why) only for a measured read-performance need.
- Give every table a primary key, and every foreign key an index — most databases don't index foreign keys automatically.
- Use `NOT NULL` and proper column types (real `timestamp`/`date`/`enum` types) instead of stringly-typed or nullable-by-default columns; let the schema enforce invariants the application would otherwise have to.
- Add `created_at`/`updated_at` timestamps to every table as a default habit for auditability and debugging.
- Model soft-deletes (`deleted_at`) explicitly if needed rather than actually deleting rows referenced elsewhere — but default to hard deletes unless there's a real requirement.

## ORM usage (Prisma / Drizzle)

- Keep the schema file as the single source of truth; generate types from it rather than hand-maintaining parallel TypeScript types.
- Select only the columns/relations a query actually needs (`select`) rather than fetching whole rows/relations by default — avoid over-fetching, especially in list views.
- Watch for N+1 query patterns when resolving relations in a loop; use `include`/relational queries or batch loading instead.
- Wrap multi-step writes that must succeed or fail together in a transaction.

## Migrations

- Every schema change goes through a migration file, generated by the ORM's migration tool — never hand-edit the production schema.
- Make migrations additive and backward-compatible when possible (add nullable column → backfill → make required in a follow-up) so deploys and old code don't break mid-rollout.
- Review generated migration SQL before applying it, especially for anything that rewrites or locks a large table.
- Never edit a migration that has already been applied to a shared environment; write a new one.

## Indexing & query performance

- Index columns used in `WHERE`, `ORDER BY`, and join conditions; use composite indexes when queries consistently filter on multiple columns together.
- Profile slow queries (`EXPLAIN ANALYZE`) before adding an index speculatively — verify the index actually gets used.
- Paginate any list query that can grow unbounded; never fetch an entire table into a serverless function.

## Serverless connection handling

- Use a connection pooler (e.g. PgBouncer, or the platform's built-in pooling) when running on serverless/edge functions — each invocation opening a raw connection exhausts database connection limits fast.
- Reuse a single Prisma/Drizzle client instance across invocations in the same runtime (module-level singleton) instead of instantiating a new client per request.
- Set sane query timeouts so a stuck query can't hold a function (and a connection slot) open indefinitely.
